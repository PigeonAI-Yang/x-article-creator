## 先拿手边的一份材料试试

在你常用的技能源码目录里克隆仓库：

```sh
git clone https://github.com/PigeonAI-Yang/x-article-creator.git
```

将克隆得到的 `x-article-creator` 目录放进助手扫描的 `skills` 目录，或在那里建立指向源码目录的链接。要给 DeepSeek Harness 和 Codex 同时使用，可以让两个入口指向同一份源码。以后按自己的口味调整标题、封面或文章长度，改一处就够。暂时只想看看写出来是什么样，也可以让能读本地文件的助手打开本仓库的 `SKILL.md`，按里面的写作流程处理材料。

第一次试，挑一个你熟悉到能判断对错的工具。给助手一段你最想替读者讲清楚的经历。下面的请求可以直接复制，把附件换成你自己的：

> 用 x-article-creator 写一篇给采购同事看的 X 长文。我附了项目链接、一张报价单和它转出来的表格。帮我判断转换后能不能直接拿去比价。请用同一行商品讲清楚怎么检查，配上读者能看清的对照图，最后给我引流短帖和回贴文案。

如果手里只有链接，也可以先试一个更小的任务：「我收藏了这个项目。先给我一个值得写的选题，告诉我为了写实测，最该拿什么去试。」这一轮拿到的好答案应该小到你马上能执行。比如取一张带合并表头的报价单，比较同一件商品的数量、单价和合计。拿到这样的题，下一次打开软件就知道该看哪里。

## 跟一篇推荐稿走一遍

以下用报价单转换做贯穿示例。它是给你重做的写作练习，文中涉及的错位是举例。你手里的工具会交出什么结果，要看实际文件。即便转换完全正确，这道题依然写得成，读者同样想知道你凭什么敢把表格拿去比价。

### 第一步，先找读者在做的那个决定

「推荐一个 PDF 转换工具」是一个主题，还没有说到谁会关心。给采购做报价汇总的人，可能每周都要从几个供应商发来的不同版式里提取数字。他在意的是月底交表前还要花多少工夫复核。给做资料归档的人写，同一个工具最值得讲的可能成了目录和页码能不能保留。你选了哪个读者，往下要拿的原件、要截的图、要回答的问题都会跟着变。

没现成题目时，技能建议从已核实的素材和读者的真实追问里找。一个平时曝光不高的账号突然有篇教程被很多人看到，先进去读评论。有人说「收藏了」当然让作者高兴，可对你准备下一篇稿帮助更大的是那句「我收到的是扫描件，这一步也能做吗」。如果不同帖子下面都有读者卡在这里，就值得拿一份扫描件补测。记下问题来自哪里，将来还能回头看文章有没有答到点上。

给这一轮定个收工信号：把项目名字从选题里擦掉，你依然说得出读者为什么要看。「采购拿到新报价单，怎么确认导出的价格没有串列」就足够开测。至于这个项目有多少颗星、支持几种格式，等写到需要它们解释的地方再查。

### 第二步，留下足以回答问题的材料

选原件时故意挑一行容易认回来的商品。如果第一列叫「运输费」，数量、单价和合计又恰好是三个不同的数，你很容易看出哪一格跑偏了。要是全表填的都是一，调换两列肉眼也难发现。一个有辨别力的小样本，常常比丢给工具一整本手册更能帮你理解它的表现。

保留原件、工具实际生成的文件，以及能对应上同一行的截图。顺手写下从哪里打开工具、选了什么选项、有没有手动改过结果。如果是第二次导出才正常，把第一次也留下。两次结果的差别往往就是教程里最值钱的一步。记录耗时时也说明从哪个动作开始、在哪个反馈出现时停表。读者拿网页上传的时间和本机处理的时间比较，只有知道这两个端点才比得明白。

只有作者演示时也能写出有用的推荐。你可以准确指出演示在哪一页展示了什么，读者要判断是否适合自己，还得补看哪一项。假如官方样例全是可选中文字的文件，而你手里只有扫描件，这个差别值得放在靠前的位置。把现有材料能回答的部分讲透，文章就有了边界，后续也有了明确的补测方向。

### 第三步，让两种标题竞争同一个开头

拿到输出后再定标题。假设样例确实出现错位，结果型可以叫《这份报价单转成 Markdown 后，一行里有两个数字换了位置》；痛点型可以叫《报价单转完能直接比价吗？先对一眼单价旁边那一格》。前者适合配一张能直接看到差异的图，后者让每天做汇总的人一眼认出自己的活。要是结果全部对齐，就换一个符合结果的标题，写清是哪种表格、用哪一行验过。原本拟好的悬念随时可以丢。

开头接着答标题留下的问题。原件长什么样，目标读者为什么想转它，最早在哪一步能看出导出结果可不可以用？交代完这几句，再介绍工具名和项目入口。读者想试的时候刚好碰到链接，比一上来读一屏功能清单更顺手。写到这里可以把第一段念给自己听一遍：如果它能原封不动地放到几十个工具的推荐里，就回到材料中挑一处只属于这次操作的细节。

### 第四步，让读者在每一步都知道自己做对了没有

文章用「是什么、怎么做、常见问题」来组织。报价单这个例子，中间最需要展开的是检查结果。只写「导出后检查格式」等于把最难的判断又交给了读者。可以把镜头拉近：在原件左侧找到运输费，沿这一行找到单价；打开导出的表格，先定位同一个行名，再看那个数字上方的列标题。数字相同、标题也相同，才算这一项对上。最后再回头看合计，防止被碰巧正确的总数骗过去。

每一步的篇幅可以不一样。上传只有一个入口时，一句话就够。牵涉到页面版式、表格识别或导出选项时，就把入口、实际输入和成功反馈放在一起，必要时给一次失败画面。读者中途发现自己屏幕长得和图里不一样，能就地确定是版本不同、文件类型不同，还是少点了一步，才有机会继续往下做。

推荐对象换成文章时，这套结构仍然能用。你最想转给同事的是哪句判断？作者用什么事实得出它？把它应用到同事手上的决定，会让他少做哪件事？带读者走一遍这个推理，再把链接指到值得细看的小节。推荐开源项目时则可以选仓库自带的最小例子，交代输入放在哪里，跑完新出现的是哪个文件，里面哪项变化表明运行成功。同样的三段，每一种推荐都保留了自己的读法。

### 第五步，给这篇长文配一条值得单独读的短帖

短帖可以只讲那一行运输费。若测试确有错位，就把原表和输出相应位置并排，点出「数字还在，抬头变了」这个发现。即便读者没有打开长文，下一次导出也知道多看哪一眼。长文再承接复现步骤、其他文件类型和修正办法。回贴最有用的一句话，是告诉已经遇到同样问题的人该跳到哪一段，而不是让他从第一行重新找起。

完整交稿还包括来源和字数回执。默认要求长文正文至少三千个汉字，计数时剔除标题、网址、代码，以及大段照贴的模型输出。如果稿子还短，最值得补的是读者复现时会问的下一句：换成跨页的表格，怎样认回上一页的列名？修正后，再导出一次还会不会错？能补测就带着真实结果回来；暂时答不了的，写清当前样例覆盖到哪里。这样多出来的几段，每一段都值得读者花时间。

## 用到第二篇时，你可能会问

**我已经有题目，还要先做一轮热点筛选吗？** 有具体问题就可以直接开写。尤其是来自同事或读者的原话，里头常藏着教程最难得的细节。对方说「我点了导出，回来看原来的文件怎么没变」，你已经知道要解释的是输出文件去了哪里。让技能从这句话入手，会比把它简化成某款软件的使用指南更容易写出有用的第一段。

**如果试完觉得这个项目不适合推荐呢？** 这个结果也值得留下。回到最初设定的读者和任务：单页电子报价单可以，跨页扫描件还需要人工整理，那么你就知道该把链接发给谁，谁又可以省下一次安装。文章可以只讲这个取舍，配一张能看懂差异的样例。能替读者排除一个不合适的选项，本身就是筛选者能提供的价值。

**需要额外购买服务，或者把 X 账号交给技能吗？** 技能以 Markdown 形式免费提供，可以在你已经使用的助手里写稿；模型和图片服务的费用取决于你选用的工具。实际截图需要宿主能打开目标界面或读取已有素材。你也可以只让助手准备稿件，在自己的编辑器里排版发布。拿到长文的永久链接后，再把核对过的链接贴回短帖，读者点开就能到正确的位置。

**怎么知道一篇稿已经可以交给别人？** 找一个没参与测试的人，只给他文章和公开可取的输入，让他从头走到第一个可检查的结果。如果他停下来问「你用的是哪个入口」，缺的就是入口；如果他做完还问「这样算好了吗」，缺的就是成功反馈。这两类问题比「写得再详细点」更好改。对方看完能用自己的样例重做，你就知道哪些段落真的帮到了人。
